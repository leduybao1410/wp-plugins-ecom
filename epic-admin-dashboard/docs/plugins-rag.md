# EPIC WordPress Plugins — RAG

> **Mandatory RAG maintenance rule.** Every change under `wordpress-plugins/` must update this file in the same task (record behavior, REST routes, tables, contracts, or note _"RAG review: no retrieval-worthy impact"_). See [AI-MEMORY-GUIDELINES.md](AI-MEMORY-GUIDELINES.md).

## Identity

A suite of WooCommerce/WordPress plugins (PHP) running on the **admin domain** `admin.epicroastery.coffee`, backing the headless Next.js storefront and wp-admin. Own git repo at `wordpress-plugins/`. Each plugin is its own directory; several also ship a built `.zip` beside it (deployment artifacts).

## Shared conventions (verify against code)

- **Shared-secret auth.** Public-write routes require the `X-Epic-Secret` header compared against a stored `shared_secret` option (constant/variant `SHARED_SECRET`). ~59 `X-Epic-Secret` references. Never expose this value.
- **Public-write guard.** The website calls `epic-agent-api` (rate-limit + honeypot) *before* accepting any public write (sample, wholesale, newsletter, order lookup). No WC order/customer is created by the guard.
- **WooCommerce owns the live retail product catalog and orders.** `website/src/lib/products.ts` reads the catalog; `website/src/lib/woocommerce.ts` handles order operations. Storefront menu and presentation mappings remain code-owned.
- **Leads go to their own tables**, not WC orders/customers. Many plugins send mail via normal `WC_Email` classes (visible under WooCommerce → Settings → Emails) and log delivery status in wp-admin.
- **`epic-rest-url-fix`** is **must-use**: rewrites only `rest_url()` from the storefront domain to the admin domain; `home_url()` is untouched.
- Most plugins expose a **REST namespace under `/wp-json/epic/v1/`** (the site-facing write/read routes).

## WooCommerce Product MCP (2026-10)

- Source: `wordpress-plugins/epic-product-mcp/`; local deployment package: `wordpress-plugins/epic-product-mcp.zip`. It registers `search-products`, `get-product`, `list-product-variations`, `get-product-variation`, `preview-change`, `apply-change`, and `permanently-delete-variation` as WordPress Abilities API tools for the existing MCP Adapter endpoint. It adds no public write route.
- WooCommerce REST API v3 controllers validate and save native product/variation fields, including `meta_data`. The plugin reserves `_epic_product_copy_{vi,en,ru,hi,zh,ko,ja}` for copy objects containing `name`, `notes`, `excerpt`, and `description`.
- `preview-change` returns exact field/translation diffs and a signed one-use token bound to the payload hash, authenticated user, record revision and ten-minute expiry. `apply-change` re-reads the record and rejects stale revisions. The revision hash excludes WooCommerce's randomized, computed `related_ids`; saved product/variation fields and translations remain revision checked. Create defaults to draft; product delete goes to Trash; ordinary variation removal sets `status=draft`; permanent variation deletion requires its separately named ability and a matching preview token.
- Product capabilities are checked per object and WooCommerce checks them again in the controller. Audit logs contain actor ID, product ID, operation, and changed field names only—never copy values or credentials. The preview requirement governs these EPIC abilities; native authenticated WordPress/WooCommerce APIs retain their own permissions.
- `website/scripts/i18n/import-product-copy.mjs` imports locale-source copy by matching WooCommerce slugs, preserves every already-present WordPress field, supports dry run, and verifies saved values. The production run matched 17 slugs; a field-by-field comparison found 219 exact matches, 20 newer WordPress values and zero missing fields. After verifying both target products across all seven live locales, 239 migrated overrides were removed from locale source parts/files and the generated dictionaries rebuilt. `localizedProductCopy` keeps a fallback for remaining or future untranslated fields.
- Codex project MCP setup is in `.codex/config.toml`; its local helper builds Basic auth from `EPIC_WP_MCP_USERNAME` and `EPIC_WP_MCP_PASSWORD`. OpenCode's existing `epic-wordpress` user-level connection uses the same endpoint and local credential mapping. Production `admin.epicroastery.coffee` has `epic-product-mcp` 1.0.1 active; authenticated discovery exposes all seven abilities. Repeated production reads confirmed stable revisions despite changing `related_ids`. No separate staging environment was provided, so staging write/permission coverage remains outstanding.
- The cross-client product editing workflow is captured in `.opencode/skills/epic-product-mcp/SKILL.md` and installed globally as `~/.codex/skills/epic-product-mcp/SKILL.md` and `~/.config/opencode/skills/epic-product-mcp/SKILL.md`. It discovers abilities through each client's configured MCP Adapter, reads by slug, previews exact changes, requires all seven translations for text edits, applies only the reviewed token, and verifies by reading again. The Codex MCP connection is configured in the EPIC project; OpenCode's `epic-wordpress` connection is user-level.
- `wordpress-plugins/epic-product-mcp/TESTING.md` is the manual staging checklist for permissions, native WooCommerce field validation, metadata, create/trash/variation behavior, signed-token rejection, stale revisions, translation import and storefront/checkout verification. Production verification currently covers authenticated discovery and stable product revisions; the full staging write/permission matrix remains unverified.

## EPIC Admin dashboard API (2026-10)

- **Security v0.1.8 (2026-10-06).** New `includes/class-epic-admin-security.php`. Sessions and authorized login grants carry `auth_version`, an HMAC of the user's current password hash and `_epic_admin_auth_epoch` using WP's auth salt. Exchange validates the grant's version and copies its captured version to the session, so credential revocation cannot mint a fresh valid token from an old grant. Password resets/changes, user deletion and deletion of WP `session_tokens` invalidate custom sessions/grants; every request also checks credential version and current administrator capability. Existing unbound tokens require a new sign-in. Settings → EPIC Admin Dashboard adds a nonce/capability-gated revoke-all action for the signed-in admin. Revocation checks DB failures and writes metadata-only auth audit events. Schema upgrades run through `dbDelta` on a version mismatch; the version marker is saved only after new columns/table are confirmed. A fifth table, `epic_admin_limits`, stores atomic minute counters: authorize 10/source and 60/global; exchange 30/source and 120/global. Source fingerprints are accepted only after the shared client-secret check, with a keyed remote-address fallback. Limit failures return 429 + Retry-After; unavailable counter storage fails closed at 503. Hourly cleanup removes expired counters/grants/sessions.
- **Private API/browser policies v0.1.8.** The exact `epic-admin/v1` namespace rejects foreign browser Origins, permits no-Origin BFF requests and same-origin WP tooling, strips default reflected CORS headers after WP's CORS callback, and sends private/no-store responses including errors. Other storefront REST namespaces retain their existing CORS behavior. On the admin host, HTTPS WordPress responses send initial HSTS max-age=300 without preload/includeSubDomains; login/wp-admin also enforce framing/object/base restrictions and publish a stricter script policy in report-only mode. Full WordPress script enforcement and MFA enrollment still need staff compatibility/configuration work. Runtime regressions: `epic-admin-dashboard/tests/security.test.php` (fake data/functions) and `tests/integration.php` (explicitly guarded disposable WordPress DB; real schema upgrade, PKCE replay, password reset and counters).

- New companion plugin: `wordpress-plugins/epic-admin-dashboard/epic-admin-dashboard.php`, implementation in `includes/class-epic-admin-dashboard.php`. REST namespace `/wp-json/epic-admin/v1`; this is a separate, administrator-session-authenticated API, not a public/shared-secret storefront write route.
- It registers five tables: `epic_admin_sessions` (hashed opaque token, credential binding, administrator, timestamps), `epic_admin_grants` (hashed login state/code, credential binding, PKCE challenge, exact callback), `epic_admin_audit` (actor/action/target/changed field names/outcome/time), `epic_admin_receipts` (idempotency and uncertain external actions), and `epic_admin_limits` (atomic authentication counters). Created/upgraded by `dbDelta`; failed grant/session/counter writes fail closed.
- Login routes: `POST /auth/authorize` (shared dashboard client secret, callback pinned to `EPIC_ADMIN_DASHBOARD_CALLBACK`, PKCE challenge), `POST /auth/exchange` (one-use grant + verifier), `POST /auth/revoke`. Browser login runs through normal WordPress sign-in and grants `manage_options` administrators only. Every protected route reloads the session, enforces 8-hour absolute/30-minute idle expiry, and rechecks `manage_options`.
- **Login redirect fix (v0.1.1, 2026-10).** `/auth/authorize` returns `login_url = wp_login_url( $target )`, where `$target` is the `admin-post.php?action=epic_admin_authorize&state=…` URL. `wp_login_url()` percent-encodes the whole `redirect_to`, so the `&state` stays inside the redirect value. The previous `add_query_arg( 'redirect_to', $target, wp_login_url() )` left `redirect_to` unencoded, so `wp-login.php` parsed `state` as a sibling param and dropped it after login — the real browser flow then hit `admin-post.php?action=epic_admin_authorize` with no `state` and died with “Dashboard sign-in expired.” Server-side direct calls to `admin-post.php` masked this.
- **Session header fix (v0.1.2, 2026-10).** The active **JWT Auth** plugin intercepts every `Authorization: Bearer …` header on REST requests and rejects non-JWT values (``403 jwt_auth_invalid_token: Wrong number of segments``), which silently blocked `/me` (and every protected route) *after* a successful sign-in — the dashboard then bounced to `/login?error=session`. The opaque dashboard session is now sent in the **`X-Epic-Admin-Session`** header and read by `require_admin_session()`; never move it back to `Authorization`. `admin-dashboard/openapi.json` documents it as an `apiKey` header (`dashboardSession`), and `admin-dashboard/src/lib/wordpress.ts` sends it when a `token` is passed. Verified end-to-end on production: full sign-in plus `/` render and `/me` 200.
- Read routes: `/me`, `/overview`, `/health`, `/audit`, and allowlisted `/records/{resource}` and `/records/{resource}/{id}`. Collections cover retail orders, shipments, products, customers, WordPress content, leads, reviews, wholesale orders, costs, distributors, coupons and newsletter records. WooCommerce customer queries request paginated totals; combined plugin collections paginate by stable source order with aggregated counts. A missing required table or post type returns `503` rather than a false empty result. Health checks the lead, wholesale, coupon, newsletter, finance, review and courier integrations. Collection access also checks operation-specific WordPress capabilities.
- Dashboard mutations also cover wholesale allowlist/VIP/pricing-level settings, existing wholesale order status changes (payment is read-only), newsletter draft editing/confirmed queue send, WooCommerce coupon editing and redemption reports, finance ledger/export, and confirmed revision-bound removal of existing lead records. Coupon Advanced Rules delegate to `Epic_Adv_Coupons_Admin_Tab::save_rules`; keep `epic-advanced-coupons/includes/class-admin-tab.php` exactly synchronized with its `epic-woocommerce-suite/modules/` bundle copy.
- Shipment calls use a per-order MySQL lock plus idempotency receipts. Pending courier operations older than two minutes are exposed as uncertain; reconciliation confirms a booking by waybill, confirms no booking, confirms cancellation, or confirms a still-active waybill before a new attempt. Never retry an uncertain booking/cancel directly. Newsletter send uses the existing background queue and delivery tracking rather than bulk mail inside the dashboard request.
- Remaining full-plan work includes complete content/media/sibling management, lead triage, full variation/invoice/fulfillment operations, broad settings edits, finance cost/distributor maintenance, uniform list sort/filter/shareability, and deployed staging acceptance. The dashboard is not ready for production launch.
- App details and auth variables are in [admin-rag.md](admin-rag.md); the current API schema is `admin-dashboard/openapi.json`. PHP/WordPress runtime checks need an installed WordPress environment.

## Gaps / traps

- `.zip` files beside plugin dirs are build artifacts — edit the source dir, not the zip.
- Some plugin dirs (`ziNTt1S1`, `zioFMbOF`) are random-named **zip exports** of older plugin builds (junk scratch files) — exclude/ignore; the repo `.gitignore` only catches `*.zip`, so they can show up as untracked. Also exclude `epic-content-writer/drafts/`, `epic-content-writer/reports/` and `epic-distributor-profit/BAO_CAO_BH.xlsx` (local working/generated output).
- REST route namespaces: only two literal `'epic/v1'` occurrences surfaced by a simple scan; plugin route registration is often multi-line — grep `register_rest_route` per plugin rather than trusting a single namespace.
- `epic-woocommerce-suite` bundles others — avoid double-activating a bundled plugin and its standalone copy (conflicting hooks).
